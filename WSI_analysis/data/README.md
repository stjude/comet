# `data/`

This folder holds the **minimal-example data** used by every analysis in this repository, plus the scripts that generated it (`gen_*.py`). It exists to let a reviewer run the actual model-fitting code (see [`../core_code/README.md`](../core_code/README.md)) end-to-end on real, representative data, **without** distributing the full underlying cohort, raw whole-slide images, raw methylation matrices, or any clinical/identifying information.

## Two important disclosures up front

1. **This is a subset, not the full cohort.** Every file here covers only a fraction of the samples used in the full study (typically a few hundred to a few thousand slides/samples, out of a much larger internal cohort), and in several cases only a single scale / a single foundation model / a reduced feature set is included (see each file's description below). The `gen_*.py` scripts document exactly how each file was produced, including exactly what was excluded and why, so that the selection process itself is fully transparent even though the excluded data is not shared.
2. **The `gen_*.py` scripts are not runnable outside our internal computing environment, and that is intentional.** They read from internal source files — raw whole-slide-image tile caches, full methylation matrices, raw clinical spreadsheets, and internal sample/subject metadata tables — that are **not** included in this repository, either because of their size or because they contain internal identifiers or other information not suitable for public release. Every such source is referenced only through an environment-variable-configurable placeholder path (never a real internal path), and the script's docstring/comments say explicitly which source is involved. The scripts are still included **as documentation of the exact cleaning/derivation logic**, so the provenance of every shared file is auditable, even though re-running them requires internal access. Once generated, the derived, reviewer-facing outputs below are all that any analysis in this repository actually needs — the `gen_*.py` scripts do not need to be (and are not meant to be) re-run by anyone using this repository publicly.

None of the files in this folder or produced by these scripts contain patient names, dates of birth, medical record numbers, internal subject/sample identifiers, free-text clinical notes, or other identifying information. Sample-level labels (disease type, molecular subtype, mutation/amplification status, survival time in days, etc.) are retained because they are the scientific content being validated, exactly as they appear in the associated publication.

## Whole-slide image (WSI) representations

### `univ2_20x_sample_reps.p` — SAMPLER representations (all tiles, single scale)

A dictionary `{slide_filename: (10, 1536) float16 array}`. For each slide, every tile was embedded with the UNI-v2 tile-level foundation model at a single scale (20x-equivalent), and the 10 array rows are the 5th/15th/25th/.../95th percentile of that embedding **computed across all tiles of the slide**. This "SAMPLER" representation compresses an entire whole-slide image (which can contain tens of thousands of tiles) into one small, fixed-size, order-independent summary vector — the representation format that most of the WSI-based classifiers in this repo consume directly.

Generated by `gen_univ2_20x_sample_reps.py`: slides are restricted to non-cell-line samples with a resolved slide file that is present in the internal tile-feature cache; the script stores everything as `float16` to keep the file small. The script's slide-selection step depends on an internal sample-metadata table and an internal slide-mapping table (neither included in this repository — see the "internal-only sources" note in the script itself), so it documents the exact selection logic but is not reviewer-runnable as-is.

### `rms_tiles/`, `NB_tiles/` — individual tile-level representations (subsampled)

One pickle per slide (`<slide_id>.p`), each containing `{"tiles": (n_tiles<=1000, 1536) float16, "locs": (n_tiles, 2) int, ...}` — the *raw, per-tile* UNI-v2 embeddings (same foundation model/scale as above), **not** percentile-summarized, but randomly subsampled down to at most 1000 tiles per slide (fixed random seed, so the same tiles are reproducibly selected every time the script is re-run) to keep the total data size manageable. `locs` records the pixel coordinates of each kept tile, which is what lets the tumor-indicator files below be matched back onto these exact tiles.

- `rms_tiles/` covers the RMS-subtype cohort (generated by `gen_rms_tiles.py`).
- `NB_tiles/` covers the neuroblastoma (NB) cohort used for MYCN-amplification prediction (generated by `gen_nb_tiles.py`).

These are the inputs to the tile-level analyses (`core_code/mil_classification_core.py`, `core_code/tile_level_classification_core.py`).

### `tum_mlda_clf.p` — pretrained tumor/non-tumor tile classifier

A small, already-fit `sklearn` `LinearDiscriminantAnalysis` model (a handful of KB) that scores a single tile as tumor vs. non-tumor from a tile-level feature vector. This is a **fixed artifact** used by `../core_code/tile_tum_detector.py` — nothing in this repository re-trains it. It contains only model weights; no patient data.

### `RMS_tumor_indicator.p`, `NB_tumor_indicator.p` — precomputed tumor/non-tumor tile masks

A dictionary `{slide_id: {(x, y): bool}}` — for every tile kept in `rms_tiles/` / `NB_tiles/` respectively, whether that tile was classified as tumor by `tum_mlda_clf.p`. Precomputing and caching this mask (rather than re-running the classifier every time a tile-level model is trained) keeps the tile-level classification code simple and fast, and makes tumor/non-tumor status a transparent piece of metadata rather than a hidden runtime side effect.

Generated once by `gen_rms_tumor_indicator.py` / `gen_nb_tumor_indicator.py`, both of which share their core logic via `gen_tumor_indicator_common.py`: for each slide, its raw per-tile foundation-model features are matched (by pixel location) against the exact tiles stored in `rms_tiles/`/`NB_tiles/`, scored with `tum_mlda_clf.p`, and the resulting boolean per-tile mask is stored.

## Methylation representations

### `meth_top5000_sample_reps.p`

A dictionary with keys:
- `probe_ids` — list of 5,000 CpG probe identifiers,
- `sentrix_ids` — list of N sample identifiers (methylation array "Sentrix" IDs),
- `beta` — `(N, 5000)` `float16` array of SWAN-normalized methylation beta values,
- `metadata` — `{sentrix_id: {"comet_id": str, "slide": str or None}}`, linking each methylation sample back to a cohort ID and (if available) a matching WSI slide filename.

Generated (once, internally) from a much larger internal methylation matrix (originally the top ~20,000 most-variable probes across the full internal cohort): the sample list was restricted to the same non-cell-line cohort used for the WSI representations above, and probes were re-ranked by variance **within that retained cohort only** (not the full matrix), keeping the top 5,000. Beta values are stored as `float16` (rather than `float32`/`float64`) to keep the file a manageable size while preserving enough numerical precision for the classifiers that consume it. The one-off generation script itself is not included in this repository, since it depends on the full internal methylation matrix and an internal sample-metadata table (neither of which are shared) and its output is already provided here — nothing in this repository needs to regenerate this file.

## Task-specific cohort metadata

These files exist so that a task-specific data-cleaning procedure (patient/sample inclusion criteria, label derivation, quality filtering) only has to be implemented and reasoned about once, in one script, rather than being re-implemented — and potentially re-diverging — inside every downstream training/evaluation script. Each one is produced by a `gen_*.py` script whose docstring spells out every cleaning step in order.

### `RMS_survival_metadata.p`

The cleaned rhabdomyosarcoma (RMS) survival cohort used by `../RMS_survival/`. A dictionary with:
- `Y` — a `(N, 14)` array of per-sample outcome/clinical columns (overall survival time, vital status, molecular subtype, age, several treatment/staging fields, risk group, and a derived 3-year-mortality label),
- `lab_ind` — the column index of the 3-year-mortality label within `Y`,
- `labels` — the 14 column names, in order,
- `slides` — the matching WSI slide filename for each row,
- `sentrix` — the matching methylation sample identifier for each row (empty string if none),
- `patient_ids` — a cohort-internal patient identifier for each row (**not** a hospital medical record number or any other externally-meaningful identifier).

Produced by `gen_rms_survival_metadata.py`, which documents (and, where the source data allows, actually re-executes) every cleaning step applied to the original clinical cohort: exclusion of one histologic subtype that is out of scope for this survival analysis, exclusion of patients with insufficient follow-up time to reliably assign the 3-year-mortality label, collapsing two risk categories into one combined "elevated risk" group, restricting to one representative WSI per patient, and dropping a small number of patients with known data-quality issues. It additionally drops any slide whose tissue sample was too small to yield a reliable slide-level representation (fewer than 500 usable image tiles), verified by inspecting the tissue footprint of the low-tile-count slides to confirm they reflect genuinely small/thin biopsy specimens rather than a data-processing artifact.

The most detailed underlying clinical spreadsheet (containing raw dates and treatment-history fields) is **not** included in this repository; the generation script references it only by an internal-storage location, which means the script documents the exact logic but cannot be re-executed outside our internal environment. The output pickle above contains only the derived, non-identifying fields actually needed for the survival analysis.

### `NB_ADRN_MES_slides.p`

The final slide-level cohort and binary label used by `../NB_ADRN_MES/` for adrenergic (ADRN) vs. mesenchymal (MES) neuroblastoma classification. A dictionary with `slides` (list of WSI filenames), `labels` (`0`=ADRN, `1`=MES), and `label_meaning`.

The underlying label-construction process is semi-supervised and is **not** reproduced in this repository: a small set of slides with unambiguous adrenergic/mesenchymal morphology on H&E was manually identified, that labeled set was algorithmically expanded to a larger weakly-labeled set via a nearest-neighbor similarity expansion in feature space, and any remaining unlabeled slide with an independent methylation-derived mesenchymal-probability score above/below fixed thresholds was labeled from that score instead. `gen_nb_adrn_mes_labels.py` calls that existing internal cohort-construction logic (referenced by internal path only) and saves just its **final output** — the slide list and its label — deliberately not re-exposing the intermediate seed slides, expansion mechanics, or per-slide probability scores that produced it.

## A note on internal source tables

Several `gen_*.py` scripts' docstrings mention two internal sample-metadata tables (a table mapping cohort sample identifiers to WSI slide filenames and methylation Sentrix IDs, and a supplementary sample table used to determine disease group/sample type and to exclude cell-line samples). **Neither of these tables is included in this repository.** On inspection, both contain internal subject/sample identifiers, age/sex, free-text clinical notes, and other fields not appropriate for public release, so they were deliberately excluded rather than shared in original or redacted form. Every `gen_*.py` script that depends on one of these tables reads its path from an environment variable with a placeholder default, and is documented as not reviewer-runnable as a result — the same treatment given to the other internal-only sources in this folder (raw tile caches, full methylation matrix, raw clinical spreadsheet). None of the runnable analysis code in this repository (the `core_code/` modeling functions or any task wrapper) reads these tables directly; they are only used by the one-off `gen_*.py` scripts that produced the files already shipped in this folder.
